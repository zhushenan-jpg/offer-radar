# JobPilot(暂定名)需求分析与概要设计

> 多 Agent 求职调研助手 · 基于 crewAI + gpt-researcher + browser-use + GLM-5.3-Flash
> 文档版本:v1.0(2026-09-05) · 状态:待确认,确认后进入开发

---

## 一、项目定位

**一句话定位**:个人求职"机会雷达"——持续监控目标公司的职位发布,用多 Agent 流水线做简历-JD 匹配分析和公司调研,产出可解释、可评测的求职周报。**辅助决策,不自动投递。**

**目标用户**:找实习/校招/远程职位的计算机专业学生(首发用户 = 自己 + 同学)。

**为什么数据源可行**:外企与出海公司普遍使用 Greenhouse / Lever 等 ATS(招聘管理系统),二者均有**官方公开职位 API,无需注册、无需爬虫**;这批公司恰好是计算机学生出海求职的主要目标。

**明确不做的事(Non-Goals)**:
- ❌ 自动提交申请(违反平台条款,且简历叙事减分)
- ❌ 爬取 LinkedIn / Boss 直聘等禁止自动化的平台
- ❌ 绕过反爬机制
- ❌ 简历代写造假(只给修改建议)

把"不做什么"写进需求,本身就是与 AIHawk / GodsScion 类项目的差异化。

## 二、创新点

诚实地说:作为学生项目,创新形式是**组合式创新 + 工程创新**,不是发明新算法。以下每一条都有"别人没做 / 做得不好"的对照,面试可辩护。

### 创新 1:可评测的匹配评分体系(核心创新)
- 现状:所有开源求职工具(含 70k stars 的 career-ops)都有"打分",但**没有一个公开过量化评测**——分数对不对,没人验证。
- 我们:定义多维评分 rubric(技能匹配 / 经验相关性 / 硬性约束 / 成长性),每维度输出 0-10 分 + **引用 JD 原文的证据链**;自建 50 条人工标注评测集,报告模型评分与人工判断的 **Spearman 相关系数、Top-10 命中一致率、校准曲线**;每次改 prompt 跑回归评测防退化。
- 价值:把项目从 "demo" 升级为"研究型工程",这一条够撑起整场面试的深挖。

### 创新 2:面向 Flash 模型的成本工程
- 现状:同类项目没人公布成本,多数拿 GPT-4 级模型硬跑。
- 我们:利用 GLM-5.3-Flash 便宜+快+1M 上下文的特性,做一整套成本优化并量化:
  - **规则前置清洗**:中文/英文 JD 都有大量样板话术("薪资面议""福利齐全"),用规则先剥离再进模型,实测 token 降幅(预期 30%+);
  - **结果缓存**:hash(JD 内容 + 简历版本) 命中即跳过评分;
  - **批量结构化输出**:一次调用评多条 JD(JSON 数组);
  - **错峰跑批**:智谱非高峰时段积分半价,调度器把重任务排到周末/夜间;
  - **成本归因仪表**:每次调用的 token 与费用入库,报告页展示"这份周报花了多少钱"。
- 产出:"成本-质量"实测数据,是别人给不出的数字。

### 创新 3:Agent 层级化(Agent-as-Tool)
- 不是把 crewAI / browser-use / gpt-researcher 平铺并列,而是**两层架构**:外层 crewAI Crew 做业务编排,把 browser-use(浏览器操作)和 gpt-researcher(深度调研)封装成内层 Agent 工具,由外层 Agent 决定何时调用。
- 这是社区少见的组合方式,也是真实的架构决策(隔离了两个底层库的 API 变动风险)。

### 创新 4:合规混合采集策略
- API 优先(Greenhouse/Lever 官方接口,零法律风险)→ 无 API 的页面才用 browser-use 兜底,且遵守 robots.txt、控制频率 → 全流程**不自动提交任何申请**。
- 对比 AIHawk 因爬 LinkedIn 引发 DMCA 争议、GodsScion 有封号风险,这是设计层面的差异化,README 里单独成章。

### 创新 5:从"一次性工具"到"持续服务"
- 现有项目基本是"跑一次出结果"。我们做成常驻的监控流水线:定时跑批、职位 diff 检测(新发布/下架)、增量推送(邮件/webhook)、低置信度评分进入人工复核队列(Human-in-the-loop)。

## 三、优化点(均带可度量目标)

| 类别 | 优化项 | 目标/度量方式 |
|---|---|---|
| 成本 | JD 样板文本规则清洗 | 实测清洗前后 token 数对比,写入 README |
| 成本 | 评分结果缓存 | 二次运行成本下降 ≥ 80% |
| 成本 | 错峰调度 + 批量评分 | 单条 JD 全流程成本 ≤ ¥0.02;月预算 ≤ ¥30(实测校准) |
| 质量 | JSON Schema 严格校验 + 失败重试 | 结构化输出解析成功率 ≥ 99% |
| 质量 | rubric 锚定 few-shot(固定打分参照) | 同一 JD 重评 3 次,分差 ≤ 1 分的比率 ≥ 90%(自一致性) |
| 质量 | 证据链引用原文 | 报告中每条评分理由可点击回溯 JD 段落,反幻觉 |
| 质量 | 双次评分一致性检查 | 两次分差 > 2 的样本自动标记人工复核 |
| 性能 | 并发采集 + 增量抓取(时间戳 diff) | 200 条 JD 端到端 ≤ 10 分钟;增量模式只请求变化的源 |
| 可靠性 | LLM 网关统一重试/超时/降级 | 单源失败不影响整体;失败源记录并跳过 |
| 可靠性 | API 限流退避、去重指纹(公司+职位+地点 simhash) | 重复入库率 ≈ 0 |

## 五、需求分析

### 5.1 用户故事(典型场景)
1. 作为求职学生,我每周五晚自动收到一封周报邮件,里面有本周目标公司新发布的职位和"最值得投的 Top 10"及理由。
2. 我上传简历和求职意向(方向/城市/远程/薪资),系统对每条新职位给出 0-100 匹配分、分维度解释和"简历怎么改"建议。
3. 我对某条高分职位点"深挖",系统生成该公司调研报告(业务/技术栈/评价/常见面试题)。
4. 系统对没把握的评分(低置信度)标记出来让我人工确认,我的确认结果回流进评测集。

### 5.2 功能需求(MoSCoW)

| 编号 | 需求 | 优先级 | 说明 |
|---|---|---|---|
| FR1 | 用户档案管理 | Must | resume.md + profile.yaml(技能/意向);二期:GLM 视觉模型解析 PDF 简历 |
| FR2 | 职位采集 | Must | Greenhouse + Lever 公开 API;公司清单可配置;去重入库 |
| FR3 | JD 结构化解析 | Must | LLM + JSON Schema → 技能/级别/薪资/地点/远程标记 |
| FR4 | 匹配评分 | Must | 多维 rubric + 证据 JSON + 置信度;低置信入复核队列 |
| FR5 | 周报生成 | Must | Markdown/HTML:新增职位、Top N、趋势、下一步建议 |
| FR6 | 公司调研 | Should | gpt-researcher 封装为工具:业务/技术栈/口碑/面试题 |
| FR7 | 定时监控与通知 | Should | 调度器错峰跑批;diff 检测;邮件/webhook 推送 |
| FR8 | 评测台 | Should | 标注集管理、一致率/校准报告、prompt 回归 |
| FR9 | 浏览器兜底采集 | Could | browser-use 封装为工具,抓无 API 的招聘页 |
| FR10 | 简历优化建议 | Could | 针对 Top 职位给修改建议(仅建议,不代写) |

### 5.3 非功能需求

- **成本**:单条 JD 全流程 ≤ ¥0.02;单份周报(约 200 条 JD)≤ ¥3;月预算 ≤ ¥30(以上为目标值,实测后写入 README)。
- **性能**:200 条 JD 采集+评分端到端 ≤ 10 分钟(并发 5-10);增量模式 ≤ 2 分钟。
- **可靠性**:单数据源失败只降级跳过;所有 LLM 调用有超时/重试;重要产物(SQLite)可重建。
- **可移植**:纯 Python 3.11+,Windows 原生可跑,不强制 Docker。
- **可扩展**:数据源 / LLM 提供商 / 通知渠道均为插件式注册。
- **安全隐私**:简历与 API key 仅存本地(.env),不上传第三方服务。
- **可观测**:结构化日志;token 用量与费用按模块归因入库。

### 5.4 关键约束
- 个人消费级硬件(无 GPU;若做 OmniParser 视觉定位加分项,再考虑免费 Colab 或放弃)。
- 智谱 API 预算有限 → 一切架构决策向成本倾斜(这本身就是项目主题)。

## 六、概要设计

### 6.1 总体架构

```
┌─────────────────────────────────────────────────────┐
│ 展示层    CLI │ Streamlit 面板 │ Markdown 周报 │ 邮件/webhook │
├─────────────────────────────────────────────────────┤
│ Agent 层(crewAI Crew,业务编排)                      │
│   Scout(搜集) → Parser(结构化) → Matcher(评分)   │
│        → Reporter(报告) ;Researcher 按需调用        │
├─────────────────────────────────────────────────────┤
│ 工具层    ats_collector(GH/Lever) │ researcher_tool │
│           browser_tool(二期) │ db_tool │ notify_tool │
├─────────────────────────────────────────────────────┤
│ 网关层    LLM Gateway(自写薄层):GLM 接入统一封装、   │
│           Schema 校验+重试、结果缓存、token/费用计量   │
├─────────────────────────────────────────────────────┤
│ 存储层    SQLite(职位/评分/报告/标注/成本流水)        │
│           profile.yaml + resume.md                   │
├─────────────────────────────────────────────────────┤
│ 调度层    APScheduler:错峰跑批、增量 diff、触发通知    │
└─────────────────────────────────────────────────────┘
外部:Greenhouse/Lever API · GLM-5.3-Flash API · 搜索 API(调研)
```

### 6.2 模块职责与"复用 vs 自写"清单

| 模块 | 职责 | 来源 |
|---|---|---|
| `collectors/` | 各 ATS 源抓取 → 统一 `JobPosting` 模型,指纹去重 | **自写**(API 很简单,别引入重依赖) |
| `agents/` | 四个角色 Agent 的职责、prompt、协作流程 | **自写**(crewAI 只提供编排引擎) |
| `tools/researcher_tool.py` | 把 gpt-researcher 包装成 Crew 可调用工具(锁版本) | **复用 gpt-researcher**,胶水自写 |
| `tools/browser_tool.py`(二期) | 把 browser-use 包装成工具(任务、白名单域名) | **复用 browser-use**,胶水自写 |
| `llm_gateway/` | GLM 接入、Schema 校验重试、缓存、计量 | **自写**(项目技术亮点之一) |
| `storage/` | SQLite schema 与 DAO | **自写**(轻量) |
| `scheduler/` | 错峰跑批、增量 diff、通知触发 | **自写** |
| `eval/` | 标注集、指标计算、评测报告 | **自写**(核心创新) |
| `app/` | CLI + Streamlit | **自写**,Streamlit 本身是现成库 |

### 6.3 核心数据模型(概要)

- **JobPosting**:id, source, company, title, location, remote(bool), url, raw_text, fingerprint, first_seen, last_seen, status
- **Profile**:skills[], years, education, desired{roles[], cities[], remote, salary_range}, resume_md, resume_version
- **MatchScore**:job_id, overall(0-100), dims{skills, experience, constraints, growth}(各 0-10 + 权重), evidence[{dim, quote, span}], confidence, rubric_version, model_version, created_at
- **Report**:period, job_ids[], top_ids[], md_path, cost{tokens, amount}

关键点:`rubric_version` / `resume_version` / `model_version` 全部落库——缓存失效、评测对齐都靠它。

### 6.4 关键技术决策

| 决策 | 选择 | 备选 | 理由 |
|---|---|---|---|
| 编排框架 | crewAI(锁 1.15.x) | LangGraph | 角色分工抽象与需求同构,开发速度优先;LangGraph 作为 v2 重构备选 |
| 存储 | SQLite(WAL) | PostgreSQL | 单机单人,零部署成本;DAO 层留好换库余地 |
| 界面 | Streamlit | FastAPI+React | 一周内出可用面板;前端不投入 |
| LLM | GLM-5.3-Flash 全流程 | 双模型分层 | 单模型先跑通并量化成本;若实测某环节(如报告综合)质量不足,再引入"评分用 Flash、综合用旗舰"的分层,该决策本身可写进文档 |
| 调研能力 | gpt-researcher 当库用 | 自研调研 Agent | 复用成熟管线;维护放缓的风险用"锁版本+隔离封装"对冲 |
| 搜索后端 | DuckDuckGo(免费)/Tavily 免费档 | 付费 API | 学生预算优先;接口可切换 |

### 6.5 评测方案(概要)
- **数据集**:50 条真实 JD(目标公司清单中抽样),每条由 2-3 人(自己+同学)按同一 rubric 独立打分取均值,存入 SQLite 标注表。
- **指标**:模型分 vs 人工分的 Spearman 相关;Top-10 集合重合率(Kendall τ);校准曲线(预测分 vs 实际采纳率);自一致性(重评分差)。
- **流程**:prompt/rubric 任何改动 → 自动重跑评测 → 退化即回滚。评测脚本进 CI。

### 6.6 风险与对策

| 风险 | 对策 |
|---|---|
| crewAI / gpt-researcher API 快速变动 | 锁定版本;所有外部能力经适配器(工具层)隔离 |
| gpt-researcher 维护持续放缓 | 已知风险(最后提交 2026-06);封装隔离后随时可换自研或 langgraph 实现 |
| 评分漂移 / 幻觉 | rubric 锚定 few-shot + 证据引用 + 双次一致性检查 |
| ATS API 变动或公司更换平台 | 数据源插件化,新增源只实现一个 Collector |
| API 成本失控 | 网关层硬预算:月度 token 超限自动停跑并告警 |
| 时间超期(课业) | 里程碑按 Must/Should/Could 分层,M1-M3 完成即达到"可写简历"状态 |

### 6.7 里程碑

| 阶段 | 内容 | 出口标准 |
|---|---|---|
| M1(第 1 周) | LLM 网关 + 单 Matcher Agent + 手工喂 3 条 JD | 结构化评分 JSON 正确产出 |
| M2(第 2 周) | collectors + 四 Agent Crew + 周报 | 一条命令产出首份自动周报 |
| M3(第 3 周) | 评测台 + 成本统计 + Streamlit + 部署 | 有评测数字、成本数字、公开 URL |
| M4(二期) | browser-use 兜底采集、定时监控推送、GLM 视觉解析 PDF | 演示 GIF + 增量周报邮件 |
